# The composer and the row under it

About the composer parts of `crates/emaki-app/src/workbench.rs`, `crates/emaki-app/src/a11y.rs`, `crates/emaki-core/src/files.rs`, `crates/emaki-core/src/limits.rs` and `crates/emaki-core/src/statusline.rs`.

## Rules

- Keep both accessibility fixes (the focus wrapper in `render_composer`, the forwarder in `a11y.rs`). Without either, macOS reports the window as the focused element and a dictation app (Kotoba, the studio's) cannot find the text field.
- The composer is Onyx's live-preview editor (`live/`, below), not the toolkit's field: the text is drawn as it reads while it is typed, and what it sends is what was typed. Tried and dropped before it: a preview block beside the text, the code editor's highlighted mode, a block-by-block editor, a CodeMirror editor in a webview (a native webview draws above every gpui overlay), and styles laid on the toolkit's field, which can neither hide a mark nor change a face or a size within a line.
- Never send a slash command down the inbox socket. Claude Code wraps every `user` frame there as a message from a peer, with or without our envelope, and the model refuses a peer's command. Type it in the session's terminal instead.
- ↩ or a click runs a command only when it acts alone (`driver::acts_alone`) and is the whole message. A skill run unasked cannot be taken back, so a name not on the list counts as a skill.
- The status line is the only write the app makes to Claude Code's settings. The script never exits non-zero and never writes to stderr, it lives at a stable path outside any checkout, and a copy run with `EMAKI_HOME` set leaves the settings alone (it would point Claude Code at its scratch tree).
- Never take a context window smaller than the tokens in it: one model id comes in two sizes.
- A thumbnail is never a crop.
- The row under the composer always takes `NOTICE_H`, so the composer does not jump as a notice comes and goes.
- Do nothing to "@path" in a message. Claude Code reads it out of a prompt itself, typed or pasted.
- "@" lists the composer's folder and nothing outside it: no link is followed out of it, and in a folder inside a repository git lists that folder alone. Every read is charged to Emaki by macOS, so a walk that wandered would ask for Desktop, Photos and every drive by name. (`at_lists_nothing_outside_the_folder`)
- `escape_at` is the one place that says how long an escape sequence is, for all four screen readers.
- Setting the textarea's value is not a change event, so bringing a draft back starts no hidden terminal. Keep it that way.

## Accessibility

- gpui-component's input frame tracks a focus handle of its own and only asks whether it contains the focus, so gpui never marks the editor as the focused accessibility node. The wrapper in `render_composer` tracks the editor's real handle with a `MultilineTextInput` role and the typed value.
- AppKit resolves the app's focused element through the key window, and gpui's window class never forwards `accessibilityFocusedUIElement` to its content view (the gap gpui-component patches for `accessibilityHitTest:`). `a11y.rs` adds that forwarder at open.

With both, the focused element is an `AXTextArea` carrying the text.

## Plain text and drafts

The composer is one `live::Editor`, as tall as its words between its fewest rows and its most and scrolling past that (`composer-room`, its scroller the editor's own `scroll`, named to the scroll router). `live/field.rs` gives the editor the names the toolkit's field answered to (`value`, `cursor`, `set_value`, `replace_bytes`), so what reads and writes the composer's text did not change.

## Live markdown

About `crates/emaki-app/src/live/`.

`live/` is Onyx's editor (`onyx/docs/editor.md` is its story), brought over without what a note has and a message does not: pictures, files in frames, cards, PDF pages, the vault. A span's marks (`**`, `*`, backticks, a heading's hashes, a link's address) hide unless the caret or the selection touches them; a heading is larger; code among words and a fenced block are in the mono face, the block on a plate with its language's mark and colors; a list has its bullets, numbers and boxes with its lines hung under them; a quote has its bar; a table is a grid.

- Its look is the window's (`composer_look`, at every draw): the chat font with its CJK face behind it, the mono face, the composer's size, strong words semibold as the conversation sets them (`Look::strong`), and the page's ground for a block of code's plate, a shade under the composer's card. Settings, Conversation, Live markdown off (`app.live_markdown`) reads the text as plain lines (`Editor::set_plain`).
- It differs from Onyx's where a message is not a note: a tag that is no style of its own and a comment stay in sight (a prompt's `<task>` is words), and lines of dashes at the top are a rule, not a YAML header (`live/markdown.rs`).
- Its keys are its own (`live::key_bindings`, under `LIVE_CONTEXT`), not the toolkit field's; typed text arrives through gpui's input handler. The composer takes what is its own before the editor does (`capture_action` in `render_composer`): ⌘↩ sends (the editor's `ToggleTask`), ↩ sends when the setting says so and runs the slash list's choice, ⇧⇥ changes the mode (the editor's `Outdent`), ↑ ↓ ⇥ → and Esc are the slash list's while it is open. ⌘B and ⌘I are the editor's, and so is ⇧⌘C, Slack's: the code the caret or the selection is in made words again, else what is selected, or the caret's word, made code (`Editor::code`, `toggle_wrap`), in the rendered editor too, and in the raw editor of a markdown file (`sublime::toggle_code`). ⌘U and ⇧⌘X are the composer's keys for the editor's `underline` and `strike`, `<u>` and `~~`. All five are one routine (`toggle_wrap`): pressed again, a key takes off what it put on, by the spans the markdown reads as whether or not it is drawn as it reads, so with Live markdown off the marks do not pile up.
- An address written bare (`https://…`, `http://…`, `www.…`) is a link, as GitHub reads one (`markdown::bare_links`; pulldown-cmark finds none). A press on a link follows it, in the composer as in the rendered editor (`EditorEvent::OpenLink`), unless the caret or the selection is in that link: it is being written, and the press puts the caret. ⌘ and a press follow it always.
- A `*` with a digit on both sides is a times sign, not a mark: `16*0.9 … 15*0.9` stays as written in the composer, the rendered editor and the conversation (`times_signs`, here and in the vendored view). Markdown reads a `*` inside a word as opening emphasis, and a letter on both sides still does, since Chinese words around bold ones have no spaces between them.
- A list's marker is drawn in the margin and never as written, so the caret never stands inside it (`floor`, `past_marker`): ← from where an item's words begin goes to the end of the line before, → from there comes back, ⌥← and ⌥→ the same, Home stops at the words, a press on the number or the bullet puts the caret before the words, and ⌫ there takes the marker off. Stepping through it, the caret stayed where it was for as many presses as the marker has characters.
- The slash and "@" marks and the spelling marks are the editor's `set_marks`, by bytes of the text, carried with the words until set again. A right click is the editor's `Menu` event: the corrections of the word the click put the caret on, else Cut, Copy, Paste and Select All (`composer_menu`).
- The placeholder is the composer's to draw, in the chat font (`render_composer_hint`): an empty editor draws its caret and nothing else.

There is one textarea, and `Workbench::sync_draft` makes it stand for whichever place is showing. On arriving somewhere else (`draft_key`: the session, or the new-session page) the words and attachment chips are put away under where they were typed (`drafts`) and what was left here comes back with the caret at its end. It runs at every draw and before `restore_prompt`, which asks whether the box is empty on a session's behalf. The sessions page draws no composer and changes nothing. Drafts are in memory only, and last until Quit: a window closed leaves them with the app (`keep_composers`, `KeptDrafts`), which runs on with no window, and the window opened next starts with them. Its first composer takes what was left there when it is empty.

⌘↩ with nothing typed on the new-session page is the plus on the folder chosen there (`send_pressed`): a session begun with nothing said, which starts no agent, so the folder's files and a shell are at hand with no agent signed in and no network. A bare ↩ that sends does not do this. The key is bound on the window as well as in the composer, so on that page it does the same with the keyboard anywhere outside a field, and the send button there, which is lit with nothing typed, does it too. The folder a session is begun in opens in the sidebar (`new_session_in`). Tried and dropped: one box for the window, whose words followed the person into the next session.

An input method's candidates (Chinese, Japanese) stand under where its composition began and stay there until it ends, as in the system's own fields: the toolkit's `bounds_for_range` answers with the start of the marked text whatever part of it is asked for. AppKit asks right after each letter, before the next frame has laid it out, and answered from that stale layout with the caret or the marked text's end, the panel jumped between the caret, the line's start and a box with its right edge left of its left at every key.

## Finding in it

The composer has no find of its own now: the toolkit's find card went with the toolkit's field. The editor can find (`Editor::set_find`, `find_step`), and a card for it is not built yet; ⌘F with the keyboard in the composer is the conversation's.

## Dictation

Emaki has none of its own. Dictation is Kotoba's, the studio's app for it, which types into the composer as into any field: the composer's two accessibility fixes are what let it find the field. Emaki's own, with its models, its key, the pill and its history, was taken out in v0.2.8; git before that has it.

## Spelling, grammar and capitals

Two entries under Composer: Auto-capitalization, and Spelling Check, whose tick turns the check on and whose languages stand under it, dimmed and out of the pointer's reach while it is off (`app.auto_capitalize`, `check_writing`, `writing_language`). `emaki-core/src/check.rs` is the part without a window. The same check, with the same switch and language, runs on a file of prose in its editor (`spelling.rs`, `docs/panels.md`, the file's editor).

- English, US or UK, is Harper's (`harper-core`): spelling and grammar, in the process, nothing sent anywhere (`check::english`).
- A mark says "this is wrong", so a rule earns one only when what it marks is wrong however the sentence is read. Harper has some nine hundred rules and many are guesses or preferences, so three things are left out: its advice on style (by kind); the rules that guess a part of speech, find a word missing, or prefer one accepted punctuation (`GUESSES`, by name); and any correction that only joins or splits words (`only_joins`). "The effect triggers" was marked for "affect", and "file system" for "filesystem". A rule that turns out to guess goes in `GUESSES`; do not answer one false mark with a special case.
- Spanish, French and German get spelling only, from the system's checker (`sys::spelling`, the Mac's `NSSpellChecker`). Windows and Linux mark nothing in those three. The words are found by the checker's request in the background, in the writing language alone (its own guess at the language let pass a word of another of the person's languages), and a word's corrections are asked when its menu opens (`sys::spelling_fixes`). Checked word by word on the main thread, with each one's corrections, a long text held the window at every pause in typing. The Mac's own grammar check was tried first and found none of a dozen plain mistakes in any of the four languages; real grammar in more languages means LanguageTool, which is a Java server or every prompt sent to someone else's.
- Only prose is checked. `check::not_prose` takes out code between backticks, fenced blocks, and any word that is a path, a command, an "@" file, a flag, a name out of code or a number; an issue touching one is dropped (`check::keep`), as is a word the person taught (`~/.emaki/words.txt`, "Learn Spelling").
- Every mark's menu ends in Ignore (`ignore_writing`). For a spelling it lasts until the app is quit, as the system's Ignore Spelling does, since Learn Spelling is the one that keeps a word. For grammar it is kept (`~/.emaki/ignored.txt`, `check::ignore_key`): the rule and the words, so the same words are still marked for another reason.
- A check runs once the typing has paused (`check_soon`), Harper's off the main thread. The word the caret ends is marked a little later than the rest. Until the answer comes, the marks move with the text (`check::carry`); marks are bytes of one text (`issues_for`) and are not drawn on another.
- The marks are the textarea's (`set_marks`, with the slash marks): a wavy underline, red for spelling and blue for grammar. A right click on one makes the input's menu what could stand there, in place of cut, copy and paste (`corrections`): corrections only, the grammar is not explained, and a grammar mark Harper has no correction for is not drawn; a correction goes in as one step for undo (the vendored `replace_bytes`).
- A correction is a change of the text like any other: the input says so (`InputEvent::Change`, silent or not) and `writing_changed` runs inside the click. So `check::typed` is handed changes no keystroke makes, with the caret anywhere, and must answer `Other` for them without slicing on trust. "mispelled" to "misspelled" (one letter in, the caret six bytes on) once sliced backwards and took the app down.
- A capital (`check::capital`) is given at the keystroke: the first letter of the message, of a line, or after ". ", "! " or "? ", and in English a lone "i". Not after an abbreviation or an ellipsis, not inside code. Only a single typed character counts (`check::typed`), so a paste, a draft coming back and an input method part way through a character (`composing`) are left as they are. A capital deleted and typed small again stays small.
- A sentence left small is marked (`check::capitals`, a grammar mark under the rule `SentenceCapital`, offering the capital): a word typed small again after a slip looked the same as one meant small, and nothing said so. Ignore is the choice to keep it small, and is kept as any grammar Ignore is. It uses the places `capital` knows and is added to every language's findings; Harper's own rule for this passes over a short sentence.
- `writing_sync` runs at every draw and notices a text set from outside a keystroke (setting the value is not a change event), so every such place is checked without knowing of it.

## Attachments

- Files first: a pasted image is written under `~/.emaki/uploads/<session>/` before anything else. Dropped or picked files stay where they are.
- They come by paste, drop and the "+" picker. `paste_attachments` is a `capture_action` for the input's own `Paste` on the composer wrapper: it takes images and file lists off the clipboard and lets text through.
- `fold_attachments` makes content blocks for a driver (images only) and `Attached file: <path>` lines for everything else, so the inbox channel, which the TUI reads as prose, still gets the path.
- A chip is a thumbnail for a picture, else its kind's tile (`pictures::kind_tile`): a glyph on a tint of the kind's color, PDF red, Word blue, a sheet green, slides orange, and so on, each color lighter in the dark appearance. The word under the name is the extension.
- A picture is any kind a person attaches, not only the four a model takes (`build::media_type_for`; `driver::IMAGE_TYPES` still decides what is sent as a picture). What gpui reads is drawn from the file; HEIC, AVIF, a camera's raw file, PSD and the like from a PNG the system makes of it once, off the main thread, kept in `~/.emaki/cache/thumbs` (`pictures::picture_source`, macOS only; elsewhere they wear the photo tile). The file pane draws them the same way.
- A pasted picture of a kind the agent cannot take (a TIFF, as some apps copy a screenshot) is kept as a PNG (`as_png`), so the agent sees it.
- `pictures::dims` reads the pixel size from the header (PNG, JPEG, GIF and WebP by hand, the rest through the `image` crate), and `fit_thumb` gives a chip's thumbnail the picture's shape (`ObjectFit::Contain`). In a transcript every picture of a prompt is one height and as wide as its shape gives within a range (`gallery_box`), so a row of them is even; past the range it is letterboxed. The size is kept in `Attachment::size` for a chip, `Detail::sizes` for a session's file, and in `Thumb` beside a pasted block's bytes.
- In a transcript, `render_attachment` draws a pasted image from the kept file when the prompt names one, else reads the block back out of the JSONL (`transcript::image_block_bytes`, cached in `Detail::thumbs`, loaded off the main thread). A block that cannot be read stays a tile and is not asked for again until the conversation is read anew: forgotten, the next draw asked again, and the whole transcript was read at every frame it was in view. Every thumbnail, in a prompt, under a tool's result and on a chip, is drawn small (`Workbench::small`, `pictures::THUMB_PX`) through the cache of its place: the conversation's (`Detail::pictures`), which goes with its tab, or the composer's, which goes once it holds no attachment. The lightbox reads its pictures whole through a cache of its own, which goes when it closes (`docs/performance.md`, Rules).
- A click on a tile or a chip goes through `preview_attachment`: a picture opens in the lightbox, any other file with the system's app for it. A picture opens among the other pictures of its prompt (`prompt_pictures`), or of the composer: ← and ↑ show the one before, → and ↓ the one after, and the set does not go round, so at either end a key that would pass it does nothing. The bar under the picture says which it is ("2 / 4") when there are more. The keys are the workbench's (`lightbox_key`), which takes the focus at the next draw after the lightbox opens (`lightbox_focus`): a field holding it would take the arrows for its caret. Every picture of the set is drawn in one place from the moment the lightbox opens, those not shown at nothing, so each is loaded before it is stepped to; a step brings the new one in over the one left, which fades under it (`LIGHTBOX_STEP`), and the bar stays where it is. One picture drawn at a time, faded in from nothing, blinked at every step: the old went at once, and the new one was still loading.

## The limits row

On the left of the row under the composer: `Context 37% (386k of 1M) · 5h 3% (4h26m) · 7d 6% (6d7h)`, colored at the thresholds of `~/.claude/statusline.sh`. No tooltip.

**Context.** The tokens are the transcript's (`Session::context_tokens`: the last assistant row's input plus cache read plus cache creation). The window is what the transcript cannot give: `claude-opus-5-5` is 200k or 1M by the session's choice, and after a `/model` to Opus the row once read 119% where the terminal said 23%. `Limits::window_for` takes the session's own window from `state/context/<session>.json` (written by the status-line script, read by `limits::session_context`), else the size last seen for the model (`learn_window`, from a driver's `result` frame's `modelUsage`), else an assumption. `Session::models` ends on the model in use, so a `/model` back to an earlier one counts; `<synthetic>` is not a model. Context files a month old are pruned at launch.

**Five-hour and seven-day windows.** Per account, from two sources, the newer winning: a driver's `rate_limit_event` frames and the terminal's status line. Claude Code writes them to no file a terminal session leaves behind; the `statusLine` command gets them on stdin and nothing else does. So `scripts/statusline.sh` is built into the binary (`statusline::SCRIPT`): it prints the terminal's line and, when `~/.emaki/state` exists, leaves the windows in `state/rate_limits.json`, written whole and renamed into place. `Limits::refresh_from_statusline` reads it on the clock (`LIMITS_SECS`) and whenever the session showing is loaded.

`statusline::ensure` runs in `Hub::start` at every launch: it writes the script to `~/.emaki/bin/statusline.sh` and sets `statusLine` to run it unless it already does, touching no other key. There is no setting. The previous value is kept in `state/statusline.json`. If the script fails, the terminal's line goes blank and nothing is blocked. The tests run it.

A source that has no word on a window leaves the one held, and Claude Code names no five-hour window between one running out and the request that starts the next. So the row draws a window through `Window::at`: past its reset it is 0% with no time, not the old window's number.

**Codex.** Its rollout says all of it, on each `token_count` row (`docs/core.md`), so there is no script and nothing is asked of Codex. The context is the last request's input against `model_context_window`; a session that has not named a window yet shows no context rather than a share of a guess. The windows are the account's, a primary and a secondary of whatever length its plan has, and the row names each by its length: `5h:` and `7d:` on a paid plan, `30d:` alone on a free one, and no `5h:` on Pro, which has no five-hour limit.

Codex keeps a limit a family of models: `codex` for the plan's shared allowance, and another for a model with an allowance of its own (Spark had one), whose `limit_name` is that model's slug. A rollout's row carries whichever limit Codex heard of last, so taking the last row as the account's showed another model's numbers. Each is kept by its `limit_id` (`model::UsageBucket`), the newest of each from any session's rollout standing for all (`Limits::absorb_codex`), and the row shows the one the session's model draws on (`bucket_for`): its own where it has one, else the shared one, as Codex's own status line does.

The driver asks the app server for every bucket as well (`account/rateLimits/read`, `CodexDriver::read_limits`: when the child is up, after each turn, and on `account/rateLimits/updated`), since a rollout's row carries one bucket at a time and a model's own could go unseen there; 0.162 answers with `rateLimitsByLimitId`, camel case, the window's length under `windowDurationMins`. The answer also says whether the plan's ordinary usage is allowed now (`ordinaryUsageAllowed`, kept as `Limits::codex_ordinary`).

What the row answers is how much further the selected model goes, so for Codex it is laid out by the model: the model's own bucket first, under the model's name, and the plan's shared bucket after it under "all models"; a model with no bucket of its own draws on the shared one, which then stands alone, as before. Codex's own status line shows the shared bucket whatever the model and lists the others only in `/status`. "Selected model is at capacity. Please try a different model." is not a limit of the person's: it is Codex's `ServerOverloaded`, the model's servers full. The numbers read fine while the model would not answer, so after a turn refused with those words the row says "<model> at capacity" in the danger color before any number, until the next turn (`Workbench::codex_capped`); and a plan whose ordinary usage Codex says is blocked says "blocked" after the shared bucket's numbers. A model whose ordinary usage is spent can be offered "Luna Reserve" (`gpt-reserve`), a bucket of its own whose `normal_model_slug` (`UsageBucket::alias_of`) names the model it stands in for.

What was learned is kept in `state/limits.json` with its time; the row says "limits as of …" once stale and `--` until a source has reported. Tried and dropped: a hand-patched script outside the repository, whose patch was lost and the row froze.

## The suggested prompt

What the empty composer says is drawn by the window over the textarea's first line (`render_composer_hint`), and the textarea has no placeholder of its own: a suggested prompt is in italics, so it reads as offered and not yet written, and a placeholder cannot be. Nothing says that → or Tab takes it, or that ⌘↩ sends.

⌘↩ sends. Settings, Conversation, "Send with" makes a bare ↩ send as well (`AppConfig::send_key`, `cmd-enter` or `enter`); ⇧↩ is a new line either way, and the slash list takes ↩ before sending does.

After a turn Claude Code sets dim, untyped words in its input. The composer shows them in that place. → or Tab in the empty box makes them the text (`Workbench::accept_suggestion`, captured before the textarea's own `MoveRight` and `IndentInline`); ⌘↩ on the empty box sends them. `read_suggestion` reads the screen on the clock while the session showing is idle in its terminal and the box is empty. `driver::suggestion_on_screen` takes the line between the prompt's two rules, after "❯", when all of it is written dim (`ESC [ 0;2 m`), which typed words are not. A path in the words is a link (`ESC ] 8 ;; url ESC \`), whose sequences once ran into the rule below and hid it. Taking the words here leaves the terminal's own suggestion in place.

## Slash commands

- A headless driver child runs `/compact` as the command it is (2.1.288 marks it `supportsNonInteractive`: a `status: compacting` frame, the boundary, a `result` with no turns, so the turn ends as usual). In `send_message` a slash command goes to `run_in_terminal` on the `inbox` and `pty` channels and through the driver otherwise.
- The list over the composer (`render_slash_help`) shows the driver's own commands (`DriverView::commands`, from `initialize`) or the folder's catalog, `BUILTIN_COMMANDS` until one is known. It follows the caret (`driver::slash_token_at`: a "/" at the start or after a space, and the name characters around the caret). Inside a sentence it offers skills only.
- `/compact`, `/model`, `/clear` act by themselves; `/code-review` is a skill, a prompt for the model, often named inside a sentence. The catalog cannot tell them apart (`builtin` covers bundled skills too). The 2.1.288 binary can: each command declares `type` `local`, `local-jsx` or `prompt`, and `driver::LOCAL_COMMANDS` is the first two.
- `Workbench::slash_pick` (↩ or a click) follows the rule above; anything it does not run goes into the text at the caret with a space after (`slash_insert`). ⌘↩ on a message that is only a command sends it as that command, a skill with its arguments included.
- Every command named is code among words, in the mono face and the accent on its plate, as the conversation draws it: in the composer by ranges on its editor (`Workbench::mark_slash`, on every change, through `Editor::set_marks`, a `live::Mark` with `code`), in a sent prompt as inline code (`driver::mark_commands`, which leaves code spans and fenced blocks alone). So is a file named with "@" (`files::mark_mentions` once sent), and a command for the agent's shell (a prompt that begins with "!") is in the mono face whole, its "!" in the link's ink, as its row in the conversation is. A token counts when `driver::slash_tokens` finds it as a word of its own (`/usr/bin` and `a/b` are not) and its name acts alone or is in the folder's catalog (`Hub::knows_command`, cache only; the catalog is read when a Claude session of that folder is opened).

## Shell commands

A message that starts with `!` is a command for the agent's shell, as Claude Code's prompt takes one: the mark wears the link's ink as it is typed, the send button the terminal's icon, and no spelling, grammar or capital is asked of it. It is typed into the session's own terminal (`Hub::type_message`), the one place it can run: a session behind the headless child goes on in its terminal, and one in a terminal of the person's, or another agent's, says where it can run instead. Until the transcript has it, it stands at the conversation's end as it will read, the command and "running…".

## "@" files

"@" at the start of a word opens the slash list's card, with its keys, on the folder's files and folders, as Claude Code's own prompt does. `files.rs` is all of it:

- `list`: git's own (`ls-files`, tracked and untracked, ignored left out) or, outside a repository, a walk that skips hidden folders and build output. Folders are added behind a slash. Capped.
- `matches`: a name starting with the words, then a name holding them, a path holding them, letters in order. "dir/" lists what is in it; nothing typed shows the top.
- `at_token_at`, `at_tokens`: `a@b.com` is not a token, and a path with a space is `@"my file.txt"`, as Claude Code writes it.
- `mark_mentions`: an "@" whose path is on disk becomes inline code in a sent prompt (after `mark_commands`), trailing punctuation left out. In the composer it wears the same marks a command does.

`Workbench::files` keeps a list per folder, read off the main thread when an "@" is first typed and again once stale (`want_files`, called from `mark_slash`, the one place every change of the text goes through). ↩, ⇥ or a click inserts the path (`file_insert`): a file with a space after it, a folder without, so the list goes on into it. The folder is the session's or the new-session page's choice (`composer_cwd`).

On 2.1.291, a message pasted with "@notes.txt" at its very end has Claude Code's own list open under it; Return still sends it and the file is read. Unknown: a pasted message ending in half a name ("@note"), which the terminal's list may complete instead of sending.

## Notices

`Workbench::notice` is the right side of the row under the composer and the only place the app speaks: "opened in your terminal", "starting claude…", "queued behind the running turn", refusals in the danger color, the update check's "Emaki x is available". With no notice it says which channel a message would take or why nothing can send. A message that went through gets no line; the transcript shows it. Every notice fades after `NOTICE_SECS`, errors too. What waits on the person sits above the card, in the tray, and the rest of what a session has going on is behind the toggles at this row's right, after the notice (`docs/live-turn.md`, The tray, The toggles). Tried and dropped: a status string in the sidebar footer, which the scanner's index and archive counts rewrote after every turn.

After a hand-off to the terminal, `come_back` brings the window forward at the next change to the transcript, armed only when the session was waiting or idle at the hand-off (while the agent works, the next change is its own).

## Probing

- `EMAKI_A11Y=1` prints gpui's view of the accessibility tree on every draw.
- A synthetic key does not reach a background window, so `EMAKI_KEYS` dispatches the list's actions through the focus: `EMAKI_KEYS="type:see @cr,down,tab,text"` types, presses the list's keys and prints what the box holds; `EMAKI_KEYS=tab` on an empty box accepts the suggestion.
- Nothing types into the box mid-run, so two sessions each holding a draft cannot be set up from a script.
- `EMAKI_KEYS="keys:i has teh apple,wait:,wait:,wait:,wait:,wait:,wait:,wait:,wait:,issues,marks"` types a keystroke a letter (so capitals are given), waits out the check, prints what is marked and opens the first mark's menu; `fix` takes its first correction and `back` is Backspace; `rightclick` is a right click on the composer's first word, made through the input's own handler (`rightclick:<x>` that many points along the line) and `all` selects everything. All the letters of one `keys:` handled in one update would arrive as one change, a paste.
- `EMAKI_KEYS="type:Hello ,ime:nihao,commit:你好"` composes as an input method does, a letter at a time through the composer's own handler, and prints where the candidates are told to stand after each (`ime:` is the marking, `commit:` its end). A synthetic key cannot reach a real input method.
- `emaki-core files <folder> [typed]` prints what "@" would offer.
- `emaki-core statusline restore` puts back the previous `statusLine`.
