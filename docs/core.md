# Core

About `crates/emaki-core/src/`: `paths.rs`, `adapters/`, `archive.rs`, `search.rs`, `explain.rs`, and the `bench` command.

## Rules

- Nothing may write a hook into Claude Code's settings. The Python daemon wrote seven, each an absolute path into the checkout; when the folder was renamed, Python exited 2 on the missing file, and Claude Code reads exit 2 as "block", so it refused every prompt.
- If a hook is ever needed, it is a binary at a stable path outside the repository that never exits 2. The status line, the one thing the app writes into Claude Code's settings, is held to the same two rules.
- The archive's old shape is still taken in. One made by the Python Emaki, or by any Emaki before v0.2.0, is moved into today's by renames (`archive::settle_layout`); nothing in it is deleted or copied.
- Nothing above the adapters (archive, search, the window) branches on the agent except to label it.
- Nothing is read from or copied into an archive until `settle_layout` says it is in shape. In the old shape a project of Claude Code's could be named `codex`, and would be taken for Codex's folder.
- `fts_query` quotes every term. People type `rm -rf`, `a:b` and a lone `"`, all FTS5 syntax that would raise mid-keystroke.
- The explainer's child is never `--bare`, and its `cwd` stays under `~/.emaki/run/explain`: it is a real Claude Code session and leaves a transcript, which that folder keeps out of the index.
- The tests never call a model.
- A remote computer's session is never copied into the archive (`archive_ref`): its copy under `remote/` keeps what its agent deletes there. Swept with the rest at quit, a remote computer's sessions were filed as this computer's and listed as archived.
- Nothing is written on a remote computer but what the person adds a remote computer for: its key in the account's `authorized_keys`, at their word and with their password, and the watch's mark in its temporary folder.
- A session's `cwd` is the folder its transcript records and never changes: the archive, deleting and putting back go by it (`archived_main` files a copy under `project_slug(cwd)`). What opens, lists or continues a session goes by `SessionRef::folder()`, where that folder is now (Moved folders). Rewriting `cwd` would make the next sweep file a second copy under another project.

## What is on disk

`~/.emaki`, in the layout the Python Emaki used but for the archive: `archive/<agent>/<project>/<session>.jsonl` plus sidecars, `logs/`, the project registry in `state/projects.json`, `config.json`, `cache/explanations.json`. `~/.emaki/index.db` was the daemon's search index; nothing reads it now.

## The archive

`archive.rs`. Every session is in it from the first time it is seen, not from when its agent is about to delete it: the deletion is silent, the app may not be running that week, and the thirty days is a setting.

- **A copy the agent still has is a clone** where the filesystem can (`clone_over`, APFS): a second name for the same blocks, made again whenever the source has grown. It takes next to no room, and it is a picture of the source and not a link to it, so nothing done to the source reaches it. Elsewhere the bytes are copied and what is new is appended. Hard links were not used: the archive would be the source's own file, and whatever cut the source short would cut the archive.
- **A source that grew is taken only when the archive is still how it begins** (`still_begins_with`). Claude Code rewrites a transcript in place at times, and one rewritten and longer was once taken as one that had grown: its new end went after the old copy, which then held rows twice or lacked some. A copy made before this is compared with its source once (`Entry::shared`) and taken again when it is not the same.
- **Nothing is set aside that holds nothing.** A copy that is not the source is kept as a generation file (`<name>.genN.jsonl`, listed as a session of its own) only when it holds a row the source lacks (`nothing_lost`); one that is merely behind is replaced.
- **One copy a session.** A Claude Code session's copy is in the folder its `cwd` names (`archived_main`), so that `cwd` must not change between sweeps: `peek` reads it from the rows between the ends when neither end has one, and a session whose rows name no folder and say nothing is not copied (`archive_ref`). Copied in its first second, before its first message, a session got a stub under its agent's folder name and then its real copy where its folder said; the index took whichever folder sorted first, and Empty Trash deleted the stub and left the session, which came back archived. Each such copy is folded into the fullest at the first sweep of a launch (`one_copy_each`): dropped when the fullest holds every row of it, else kept beside it as a generation. The index takes a session's fullest main copy (`index_all`), and deleting names every copy in every project's folder (`everything_of`).
- **A copy the agent no longer has is packed** (`pack_stale`), a day after it was last written: it is the only copy, takes its full size and never changes again. The filesystem does it (`ditto --hfsCompression` on a Mac, `compact` on Windows, nothing on Linux), so the file keeps its name and every reader, ours and any other program, gets the same bytes. On a Mac the packed copy is made beside the file and compared byte for byte before it takes its place. A `.gz` beside the file was not used: a dozen readers go by a transcript's name and seek in it.
- **Archived** means the agent does not continue the session until it is unarchived, wherever it is: Claude Code's are kept by Emaki alone (`kept`), Codex's are in Codex's own `archived_sessions` (the adapter's `list` flags them). The window asks the adapter (`Adapter::archive`, `unarchive`, `delete_own`), so Codex makes every change to its own sessions (`codex::thread_call`: `thread/archive`, `thread/unarchive`, `thread/delete`) and keeps its records of them.
- **Codex's sessions are not copied** (`archive_ref`). The archive is for what an agent deletes by itself, and Codex deletes nothing by age: its own files are the only copy, archived or not. What an Emaki before v0.2.5 kept in `archive/codex/` is not read, and a Codex session that one archived is not brought back.
- **Archived at the person's word**, a Claude Code session leaves its agent's folder now (`release`). Every file to be removed is first read against its copy, all of it, and nothing goes unless all are the same; a file the archive does not keep (anything in the session's folder but its sidecars) stays. It is the one time Emaki removes a file of an agent's, and only ever a whole session's. **Deleted** (`adapters::delete_session`), Codex deletes its own, and everything else of the session is named for the trash (`everything_of`): Claude Code's files first, so a sweep under way has no source to copy again, then the archive's with its generations, the markdown rendered from it and its uploads. A session with no id names nothing: its uploads folder would be everybody's.
- **Unarchived**, a Claude Code session goes back to Claude Code's project folder for its folder (`restore`; `claude_project_dir`, the path with every character but a letter or a digit a dash, as Claude Code names it). The sidecars go first and the transcript last, each copied beside its place, compared, and moved in. Each is dated now: with its old date it would be past the agent's thirty days and deleted the next time the agent starts. Nothing the agent has is replaced, and the archive keeps its copy, which the next sweep finds the same as the source. An archived session whether Claude Code deleted it or the person archived it is the same thing on disk, so one restore serves both. A Codex session is unarchived by Codex, which dates it now itself. The window then counts the session as having nothing behind it (`Hub::mark_ended`): a turn it was cut off in, dated now, would read as one at work.
- **The trash** (`trash.rs`, `state/trash.json`): a session deleted in the window is archived (`Adapter::archive`, so its agent no longer lists or continues it) and recorded with when, and the window lists it in the Trash alone. Put back, it is unarchived only when deleting archived it, and its record goes. Thirty days after it was deleted the scanner removes every file of it for good (`purge_due`, at launch and hourly): Codex deletes its own, and the rest is unlinked, not handed to the system's trash, since this is the trash. One that could not be archived (a terminal of the person's still writing it) is recorded all the same and removed whole when its days are up.
- **When** is the hub's (`spawn_scanner`): every session at launch and at quit; after that a session whose file changed, once its turn is over, and one still at work every five minutes. The scan every few seconds is the window's and only reads sizes and times.

The markdown a session renders to is byte-identical to the Python renderer's except JSON key order inside tool arguments and the `You (web)` label, now `You (emaki)`.

## Adapters

The shape is borrowed from Wake (`iAmCorey/Wake`): an `Adapter` knows an agent's data roots, lists sessions cheaply, peeks one, and parses one into the shared model. Claude Code and Codex exist. A new agent is a new file under `adapters/` and a variant of `AgentId`.

The agents a machine can have, read or not, are `agents.rs` (`docs/agents.md`).

The archive is a folder an agent, `archive/claude/` and `archive/codex/`, and in each a folder a project. Until v0.2.0 Claude Code's projects were at the archive's top and Codex was in `_codex`, the underscore keeping it apart from a project's name. `settle_layout` moves that shape into this one in two steps, so that stopping anywhere leaves something the next call finishes: first every folder without an underscore goes into `_claude` and `.layout` is written, then the underscores come off. A project an older Emaki leaves at the top afterwards is taken into `claude/`; a file both have comes in as a generation unless its bytes are the same.

Gemini CLI had an adapter for one commit and lost it: in June 2026 Google closed that program to personal accounts, so most people could not sign in to it.

### Codex

`adapters/codex.rs` reads a rollout (`~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl`).

- **A rollout says most things twice, and the items are the source.** What the model was sent and what it answered are `response_item` rows, which every Codex writes. A newer one also writes what happened as `event_msg` rows of type `item_completed`: the prompt, each thing the agent said (commentary and the final answer, both shown), each thought, each command run, each file changed. A response row that says what an item already said is dropped; one with no item to match is read as it always was. This is decided row by row, not once a file: a rollout moved up from an old Codex has the prompt's row before the turn starts and its item after, and a session imported from Claude Code has items for some turns only.
- **A tool call is drawn as Claude Code's would be.** A command (`CommandExecution`) is a `Bash` call; a patch (`FileChange`, or the `apply_patch` call of an older Codex) is a call a file, `Write` for one added, `Edit` for one changed, with hunks in the shape of `structuredPatch`; `request_user_input` is an `AskUserQuestion` call with its answers; a plan is an `ExitPlanMode` call. The window and the markdown need nothing of their own for Codex.
- **Code mode.** Codex 0.162 has the model write a script (`custom_tool_call` named `exec`) and runs its tools from it. The items after the script say what it ran, and the script's own call is dropped once one has. What only the script has is what it printed: where it ran one command and that command's own output is empty, the print is the command's output. A command the sandbox refused leaves no item, so a script with none is shown itself: as the command, when all it does is run one, else as the script under its first line.
- **A command that outlasts its script's wait is one call.** The script that starts it gives up waiting after ten seconds and a second script only waits on it (`write_stdin` with nothing typed); the command's item comes under that one. The item takes the place of the first script's call, where the command began, and a script that only waits is no call.
- **A setting's change is written when it is made** (`thread_settings_applied`), not with the next prompt as Claude Code has it, so the window says no mode of its own for Codex (`Workbench::unwritten_mode`). A model is named as Codex's list writes them (`driver::model_label`).
- **A stop is written before the command it cut short.** The item of a command stopped mid-run comes after `turn_aborted`; it is put above the stop's line, which stays the last thing the round says.
- **A plan has no answer in the rollout.** The last one waits (`Pending`). The next prompt settles it: sent out of plan mode the plan reads as approved, sent in plan mode as not approved. That is read off the mode, not off anything Codex records.
- **What a session is set to** is in `turn_context` and `thread_settings_applied` rows. `Session::mode` is one key: `plan` in plan mode, else the permission profile's id without its colon (`read-only`, `workspace`, `danger-full-access`, or a profile of the person's by its name), else the same three from the sandbox policy an older row names. The first value is where the session began; a later one that differs is a line at the foot of the round before, as for Claude Code (`docs/modes.md`).
- **A turn's ends are explicit**: `task_started`, then `task_complete` or `turn_aborted`, kept as `Session::turn_open`. A `task_complete` with an `error` is a turn that failed, and the round ends on the error. `adapters::turn_state_from_session` goes by `turn_open` where there is one, since words said in an open turn are commentary and not the reply; a rollout without those rows is read off the model's tail as before.
- **Tokens**: `token_count` rows are running totals with cached tokens inside `input_tokens`. The last request's `input_tokens` is the context in use, and `model_context_window` the size it is in. The same row carries the account's usage windows (`rate_limits`: `primary` and `secondary`, each with its length in minutes, either of which can be null), kept as `Session::usage_windows` for the row under the composer (`docs/composer.md`). A row can have the windows with `info` null.
- **The title** is the thread's name when the person gave one. Names are not in the rollout: `session_index.jsonl` has a row a naming, the newest last. Nothing else in Codex's home is opened.

## Moved folders

`moves.rs`. A folder renamed or moved leaves its sessions naming a path that is gone: Claude Code keys its project folder on the path (a rename makes a new one, and asks about trust again), and Codex keeps `cwd` in each rollout's first row. Nothing of theirs is rewritten. Both continue a session from the folder they are started in: `claude --resume <id>` finds the session in any project folder, keeps writing its original file and stamps the rows it adds with the new `cwd`; Codex takes the new folder as `cwd` beside the thread id on `thread/resume`.

- **A move found is kept** in `state/moves.json`, old path to new, by the scanner and with nothing asked: what changes is Emaki's listing alone, and the person can take it back (`docs/window.md`). One taken back is kept as going nowhere (an empty new path, `take_back`): it is not applied and not found again, and it says nothing of its parent's move. `index_all` reads every session's `cwd` through it into `SessionRef::moved`, a folder inside the one moved going with it. A path that exists again is where it is: a folder made anew at an old path is its own project.
- **When it is looked for**: at launch, when the folders the sessions name change (a session begun in a folder renamed is how a rename shows), and when a session whose folder is gone is opened (`Hub::look_for_moves`); never by the clock. A folder nothing could place is not looked for again until the folders change. Each find is kept and the index read again, and what moved is looked at once more, for the folders its move says of (`HubEvent::Relocated` goes before that index).
- **How it is found** (`survey`, over the folders that are not temporary): the folder by its identity first, since a rename on one disk keeps its device and file number, which `state/folders.json` holds for every folder seen while it was there. A live project's folder with that identity is it, and on a Mac the system says where it went with no session begun there (`/.vol/<dev>/<ino>` and `F_GETPATH`); a folder found in a Trash is not taken. Then the parents a move says moved: once `a/old/x` went to `a/new/x`, `a/old/y` is looked for at `a/new/y`. The pair can be a kept move or a gone folder and the one live folder with its name, taken only when the gone folder's parent is gone too. Off Unix there is no identity, and names alone guess.
- **The project's key does not change.** `state/projects.json` keeps every path's slug, so the archive and `ui.json` keep theirs; a moved session's project is its new folder's (`SessionRef::project` goes by `folder()`). What the window shows is a label (`Workbench::relabel`).

## Connected Devices

`remote.rs`. Other computers whose sessions the window lists, reads and runs, over the system's own `ssh` (`state/remotes.json`, Settings, Connected Devices; a target is kept there only once it answers). Nothing of Emaki's is installed there: the computer needs its ssh server, a key this one signs in with, and the agents.

- **A remote computer's folder is written `ssh://<remote>/<path>`** wherever a session's folder goes (`remote::folder`, `split`; `SessionRef::remote_id`). So a project there is a project of its own beside one at the same path here, and what starts an agent knows where to. `paths::absolute` takes it whole. The moves survey, the archive and the folder checks of this computer pass it by; `remote::is_there` answers for it, true for a remote computer in Settings.
- **Its sessions are copied here** as they are written, into `remote/<id>/` under its home's own layout (`.claude/projects`, `.codex/sessions`, `.codex/archived_sessions`, `.codex/session_index.jsonl`), and read as the agents' folders are (`ClaudeAdapter::at`, `CodexAdapter::at`, `adapters::for_ref`). `index_all` lists them after this computer's, none of a remote the person disconnected, with their folders written as the remote computer's; an Emaki there has its explainer's sessions too, which are left out. A transcript is taken by what was added to it, checked against the last bytes of the copy; anything else whole; a file is dated as it is there. What Claude Code deletes there stays here, as the archive keeps what it deletes here. Codex deletes nothing by age, so a Codex file gone from the remote computer goes from the copy (`prune`): it was archived or deleted there.
- **The link** (`remote::Link`, a thread a remote computer, started by `Hub::link_remotes` at launch and when the remote computers change, and none for one the person disconnected, `Remote::off`): the remote computer is asked what it has (`probe`: its login shell's `PATH`, asked as a terminal there has it, interactive so a `.zshrc` counts, its home, its system, both agents and their versions; kept in `probe.json`), everything is copied, and then a watch runs there until the link breaks: a POSIX script that every second prints the copied files changed since the second before (`find -newer` a mark of its own in the remote computer's temporary folder, `stat` as BSD or GNU says it) and a `.`, so a broken link is known by its silence and the script ends at its next write. Each change is copied as it is told. A break is tried again after five seconds, doubling to two minutes; Try Again goes at once. Never by the clock from here: the remote computer says when.
- **One computer, every way to it** (`Remote::ways`, `Way`): a name on the network at home and a name on a private network (Tailscale) that reaches it from anywhere are two ways to one computer, kept as one remote with one id, so its copy, its sessions, its tabs, its files and its agents' sign-in (which live on that computer) are the same whichever way reaches it. The probe asks the computer's own id (`Probe::machine`: a Mac's hardware UUID, else Linux's machine id), the same by every way; an address that answers with the id of a computer kept already is added to that one (`settle`), and two kept from before become one when either answers (`join_same`, from the hub's link status), the one kept first staying and the other's copy left on disk unread. A probe from before the id was asked is matched by the computer's name, home and system. The person picks the way: `Remote::using`, kept in `remotes.json`, is the one every command takes (`Remote::way`), and nothing falls back to another, so a way is changed by disconnecting and connecting by the other (`connect_by`). An address added to a computer connected by another way leaves it on that one (`keep_in`). An address with no account is kept with the account that answered by it (`Probe::user`, `id -un` there; `settle`, and `fill_account` for one kept before), so it signs in as the same account from a computer whose own is named otherwise, and typed again with no account it is the same way (`draft`). A computer is named as its person names it, a Mac's Computer Name (`Probe::computer`, `scutil --get ComputerName`), else by its host's name; one kept under its host's name before the Computer Name was asked takes it once. A computer removed is remembered beside its copy, which stays (`remember`: its name in `remote/<id>/name`, beside its `probe.json`): saved again by any way, it is known by its own id and takes back its id, so its copy and its sessions, and the name it had (`revive`). Nothing of a password is kept; what lets this computer back in with none is its key in the other's `authorized_keys`. Whatever holds a remote for long asks for it again before each command (`remote_files::Engine::now`), or it went on by the way it started with. A link stopped says nothing more, or a probe it was still waiting on said Failed over the new link's Connected.
- **A remote that says nothing is not waited on.** `probe` first asks for a word back within `REACH` (five seconds), and ssh gives up on a connection in as long (`ConnectTimeout`) and on one gone quiet in fifteen (`ServerAlive`); a watch with no line for fifteen seconds is ended and made again. A computer asleep or locked kept Connect at Connecting… for a minute and more.
- **ssh** (`remote::ssh`): `BatchMode` (a key signs in, nothing is typed), `StrictHostKeyChecking=accept-new` (a new remote computer's key taken once and checked after), keep-alives, compression, and on Unix one connection a remote computer shared by every command but a terminal (`ControlMaster`, a socket in `run/ssh`), so each after the first starts in milliseconds. A terminal has a connection of its own: through the shared one, a new size never reached the remote (OpenSSH 10), and Claude Code there drew for the size it began at, its lines wrapping a character late and its prompt drawn over the rows under it. Every script runs under `/bin/sh` whatever the account's shell is.
- **Letting this computer in** (`install_key`): the key the agent holds, else `~/.ssh/id_ed25519`, made when there is none, added to the account's `authorized_keys` as `ssh-copy-id` adds it, with the password handed to ssh alone through `SSH_ASKPASS` and kept nowhere. Off Unix, by hand.
- **The agents' sign-in there.** The probe asks `claude auth status` and `codex login status` too (`Probe::claude_signed_in`, `codex_signed_in`); Codex says it on stderr, its first line "Logged in using …" or "Not logged in". `check_sign_ins` asks both again with nothing else. A sign-in there runs inside a watcher (`Start::Watched`, `WATCHED`): with no terminal there a program does not hear its ssh end, and a sign-in waits for minutes, so the script hands the agent each line it is sent through a pipe of its own and ends it when what it is sent ends, or when the script itself is hung up on, killing it outright if it is still there two seconds later. A sign-in left by a cancel, a closed window or a quit app ends there with its connection. Claude Code no longer ends on a code it refuses: it says why and asks again, so a line said after the code with no end in a few seconds is taken as why (`Login::finish`). Codex signs in there by `codex login --device-auth` (`Login::start` with `AgentId::Codex`), which prints a page and a one-time code (`device_code`) and ends once the page has the code (`Login::wait`). A Mac keeps Claude Code's sign-in in the login keychain, which is locked to an ssh session, so Claude Code there says it is signed out over ssh even when it is signed in at that Mac's screen. Settings signs it in from here (`remote::Login`, `docs/window.md`): `claude auth login` there with no terminal prints the page to sign in at and waits for the code the page shows. The page opens in this computer's browser (`BROWSER` there is a program that does nothing, so none opens at its screen) and the code is typed in Settings; `check_sign_ins` asks again after. With the keychain locked, Claude Code writes the sign-in to `~/.claude/.credentials.json` (it asks `security show-keychain-info` and takes exit 36 as locked), which every later ssh session reads.
- An agent there (`agent_command`) runs in the folder with the login `PATH`, `CLAUDE_CODE_ENTRYPOINT` set as here. How the window reaches it is `docs/channels.md`, A session on a remote computer.
- **Its registry's records** (`.claude/sessions/<pid>.json`) are copied with the rest, never the key files beside them, which hold each inbox's token; a record of a process that ended goes from the copy at the next full listing (`prune`). The hidden terminal finds its own there (`docs/channels.md`).
- **A file that changes or goes as it is read** is said with the length it has, and left as it is: the watch tells of it again. Taken as a broken link, every record of a Claude Code that ended there dropped the link and made it again.

### A remote computer's files

`remote_files.rs`. The files panel, the editor, every preview and git's marks read a remote computer's folder from a copy of it here, `~/.emaki/remote-files/<remote>/<path>` (`local_of`, `place_of`), beside `remote/` and not in it, since the hub's watcher on `remote/` wakes the scan. The copy is kept the same both ways, so nothing that reads a file needs to know it is a remote's.

- **Only what is looked at is copied.** A folder is copied when the tree lists it (`want`, from `list_dir`): its files and the names of the folders in it, and those folders are followed from then on. A file over `BIG` stands empty until it is opened (`open_file`, from `show_file`), and the pane reads it again when it is in. A session whose folder is the home there copies the home's first level, not the home.
- **An engine a remote** (`Engine`, started the first time a copy of its is asked for): it lists each folder wanted and not yet listed, then runs a watch there that every second lists each wanted folder something in changed (it, or a thing in it, `-newer` a mark), and makes the folder here the same: a file that differs there is copied, one copied before and gone there goes here. A file is written beside the copy (`.parts-<remote>`) and moved in, so nothing reads half of one. The link it uses is the shared ssh connection; a break is tried again after five seconds, doubling to a minute, and the copy as it stood is shown meanwhile.
- **What was the same both ways** is kept a file (`Entry`: its size and time there, its length and time here, in `.<remote>.json`). A file that differs from it here was changed here and is sent; one that differs there is copied; both, and the remote's wins, since the agent works there. A file's time here is left as the save made it after a send: changed under it, the editor read the file as changed on disk.
- **What is written here goes there**: a watcher on the copy hands each path written or made to the engine, which sends a file that differs (`send_file`: beside it in the temporary folder there, then moved in with the mode it had) and makes a folder made, with what in it was never sent. A removal here is never sent: only the tree removes, and it does so through `moved`.
- **The tree's moves are made there first** (`moved`, called by `fsops::move_path`, which every make, rename, move, copy in and removal of the tree is). Within one remote it is `mv` there. Out of the copy, which is a removal into the holding folder, the thing goes to the remote's trash (a Mac's `~/.Trash`, else the freedesktop trash with its `.trashinfo`, else `~/.emaki-removed`) and taking it back brings it from there. Into the copy from anywhere else it is sent. Between two remotes it is refused.
- **Git runs there** (`git::at`): for a folder of the copy every git command is git on the remote in the folder itself, over ssh, with any path of the copy given as an argument made the path there, and `top` made the copy's again. The copy has no repository (a `.git` there is an empty folder, which is how a checkout is known), so status, diffs, marks, commits, branches, fetch and push are all of the remote's, and the copy follows what they do to the files.


## Presence, without hooks

There is no daemon. A session is live by the registry, by a driver of our own when we started the process, and by a grace after its newest row for anything else (`SessionRef::active`; a file's time is not it, `docs/transcript-format.md`). A fresh file with neither is a session that just ended (an interactive Claude Code always has an inbox), so the composer offers to resume it.

A `statusLine` command cannot block anything: if it fails, the terminal's line goes blank. The status line is described with the limits row, in `docs/composer.md`.

## Search

`~/.emaki/search.db`, FTS5, one document per item (a prompt, a reply paragraph, a thought, a tool call): coarser and a hit in a long session says nothing about where to look, finer and snippets lose context. A hit is a matching document, not a term occurrence. Sync is incremental on (size, mtime), on its own thread. A session is read whole to be indexed, so in the app one still being written waits its turn (`sync_paced`): indexed at most once a minute while its file changes and as soon as it has been still for ten seconds. An agent at work writes every few seconds, and a session of 249 MB was parsed whole that often. A trailing `*` survives the quoting as a prefix match.

## Opening time

Tried and dropped: a tail-first reader. The largest transcript on the machine this was built on (137 MB) reads in about 80 ms and builds in about 80 ms more. Bring it back only if bench shows a session over about half a second.

## The explainer

`explain.rs`: opaque tool calls in plain words.

- Asked about: a `Bash` heredoc, a piped chain, anything with an opaque shape (`OPAQUE_MARKERS`) or longer than `explain.min_chars`. Simple calls get a canned line from their own arguments (`explain::canned`) and never reach a model.
- The call: `claude -p --model claude-haiku-4-5` with a fixed system prompt, no settings, no MCP servers, no tools.
- Whose model answers (`explain::helper`), for the explanations, the outline's labels and its overview alike: the session's own agent's, and nobody when that agent is not installed. Which of its models is the person's choice, an agent at a time, in Settings, Model calls (`explain.model`, `explain.codex_model`, read through `Explain::chosen`). Both are read against the agent's own list as it last gave it (`explain::helper_model`): a model it no longer offers, retired or not on the person's plan, is never asked for, and the default is used. The default is the agent's fast one (`fast_model`): for Claude Code `FAST_CLAUDE` (Haiku 4.5) while its list has it, else the first the list calls fast; for Codex the first its list calls fast. `FAST_CLAUDE` was written into every settings file as the model before there was a choice, so it reads as none chosen. The two are never crossed: with both installed Haiku once answered for Codex sessions too, which spent one account on the other's work. So a caller says which agent the session is (`Explainer::request`, `outline::summarize`), and `run_child` is the one place that chooses; the command line a caller builds is Claude Code's either way.
- The Codex call (`codex_argv`): `codex exec`, ephemeral so no session is kept, without the person's config or rules, in the read-only sandbox, at low effort, with the system prompt and the message as one prompt, and the answer read from the file `--output-last-message` names. With none chosen, the model is the first Codex's own list calls fast (`codex_light_model`, from `cache/options.json`), since its names change with every release; with no list yet it is Codex's default.
- Explanations are asked for the calls waiting on a card and nothing else. Settings had a section to choose "off" or "every new call"; it was removed and `Workbench::new` sets the scope whatever the file says.
- Explain tool calls in Settings, Model calls, is `explain.enabled`, on unless turned off. Off, no call reaches a model: tool cards have no Explain button, a permission card shows only the free line `canned` makes, and an answer cached before is not shown either. The switch hands the explainer its new settings at once (`set_explain`).
- Answers are keyed by a hash of the call's name and sorted arguments and kept in `~/.emaki/cache/explanations.json`, bounded. `Explainer::lookup` is cache-only and `attach` folds cached answers into a loaded session, so a command explained once is explained wherever it appears.
- `paths::is_explainer_cwd` makes the index drop the child's sessions, and `prune_transcripts` sweeps their files hourly.
- The hub owns one `Explainer` and asks it the moment a `Permission` event arrives, so the card has the answer while the person decides. A tool card's *Explain* button asks with `force`. Scope `all` also asks for the tail of the session showing on each live reload, never on a first open.
- Answers come back as `HubEvent::Explained` into `Workbench::explanations`, an overlay by call id that the next load makes redundant.

## Memory reports

A leak that grew to 14 GB on one Mac while typing (issue 8) could not be reproduced on any other, and the person had nothing to send: what grew has to be measured where it grew. So the window reads its own footprint on its one-second clock (`memory::footprint`: `proc_pid_rusage` on a Mac, the number Activity Monitor shows; the resident set on Linux; nothing on Windows, which writes no report) and, at `FIRST_REPORT` and at each doubling after it (`report_due`), writes `~/.emaki/logs/memory-<time>.txt` off the main thread (`write_report`). Two reports of one run show what grew between them; the newest twenty are kept.

- A report holds the app's version, the footprint, what the window holds in counts (`Workbench::memory_held`, `Hub::held`: tabs, each conversation's rounds and items, transcript rows, pictures, each place's pictures as drawn and their decoded size, file lists, drafts, drivers, terminals) and no words of the person's, then the system's view: `sw_vers`, the machine and its memory, the displays and GPU, and `footprint` and `vmmap --summary` of the process. Both tools read a notarized, hardened Emaki run by the same user.
- Each report puts a line in the tray (`memory_line`, `docs/live-turn.md`): the size first, so it survives a narrow row, Reveal in Finder and Close.
- Counts taken from the hub are taken a lock a statement: the locks in one `format!`'s arguments are all held to its end, and `terminals` with `peers` stands against `reap_terminals`.

## Probing

- `emaki-core remote` lists the remote computers; `remote add <[user@]host[:port]> [--password <pw>]` adds one as Settings does, `remote link <id> [--secs <n>]` copies its sessions and follows them, printing how the link stands, and `drive ssh://<remote>/<path> <words>` runs a turn there.
- `emaki-core bench [<id>...]` times read, build and render for a transcript (the five largest by default).
- `EMAKI_TIMING=1` makes the app print load and hand-over time per open.
- `emaki-core explain <command>` makes one real model call from a terminal. It asks as a Claude Code session would; `EMAKI_HELPER=codex` asks as a Codex one.
- `EMAKI_MEMORY_REPORT_MB=<n>` writes the first memory report at that many megabytes, so a probe copy writes one at once.
